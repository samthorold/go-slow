A slow-news briefing: a Go web app, hypermedia-driven with htmx, storing the Record in SQLite.

## Where things are

- [`CONTEXT.md`](CONTEXT.md): the domain language (Briefing, Owner, Story, Item...). Use its terms in code, tests and issues.
- [`docs/system-design/README.md`](docs/system-design/README.md): the design, its end state and hypotheses, and why it has its shape.
- [`docs/research/`](docs/research/): research that grounds the design.
- Code:
  - `cmd/go-slow`: `main`, the composition root. It alone reads the environment.
  - `internal/config`: the typed config.
  - `internal/web`: the web adapter and the app's constructor, `web.New`, with its templates and the vendored htmx.
  - `internal/collect`: Collection, the Sources list with each one's terms (licence, attribution, what may be kept) and rate limit, reading each feed format (Atom, the ONS release search, Parliament's written statements) and the *No Source goes quiet* check, with its ports (`Fetcher`, `Store`). A Source whose feed carries only a summary declares how each entry's full text is fetched (`Source.Text`, `text.go`: GOV.UK's Content API document for the entry's path, or the written statement itself), and a new entry is kept only once its text is fetched, through the same `Fetcher`; one whose fetch fails is left out, and the feed's validators are not saved, so the next run sees it again. `Backfill` (`backfill.go`, its port `TextStore`) gives the text to unread Items collected with only a summary. Its timetable runs inside the app process, started by `main`.
  - `internal/interest`: the Owner's Topics and Depths, and the lazy-reading check that ties Items to Topics with no model call. Collection runs the check after every run; taking up a Topic, or changing its Depth, re-runs it for that Topic over the Items not yet read.
  - `internal/feedback`: the Owner's Feedback. `Service.Give` validates which kinds each level takes, keeps the piece as given (with its Depth and when), and applies its `Effect` (worked out by `EffectOf` from the piece alone, so a changed mechanism can be re-run over all of it), in one transaction through its `Store` port. Effects are marks naming the Feedback (`withdrawn_by`, `unwanted_by`, `missed_by`), never deletions; the storage adapter keeps withdrawn records out of every act's queries. Given inline on the Briefing (`POST /briefings/{day}/feedback`) and a Story's page (`POST /stories/{id}/feedback`), each answering `303` back to its page or `422` with the page re-rendered around the failed form; `GET /feedback` lists it all as given. `Service.Undo` marks a piece undone (`undone_at`, kept, never deleted) and the storage adapter's `lift` works each mark it made out again from the Feedback still standing (the earliest standing piece that makes it, or none), so a mark another piece makes stays; what an undone *missed* added is withdrawn by it and shown nowhere. Undone from each page that lists it (`PUT {page}/feedback/{id}/undone` on the Briefing, a Story's page, a Sunday read, and `PUT /feedback/{id}/undone`), answering `303` back. Undone Feedback is never precedent and the register does not count it.
  - `internal/register`: the register. Each hypothesis of the end state read from the Record by its declared reading rule (windows counted from the first Briefing), pure code over a constructed `register.Record`, shown at `/register`. Status lives only here, derived on every view, never stored. Opening a Briefing or a Sunday read is kept as a side record, once per day; commits come from the `commits` admin command (below), which also marks the commits that change the Editor (`internal/editor`, `internal/claude`, `internal/feedback`, `internal/sqlite/feedback.go`).
  - `internal/claude`: the Claude model adapter (Anthropic's Messages API and Message Batches API through `anthropic-sdk-go`, structured output against the act's schema). Anthropic's types stay inside it. Its `Turn` (the `Conversation` port) uses the beta Messages API for strict tools, adaptive thinking at high effort, `fallbacks: "default"` on a refusal and prompt caching; a manual loop in the Editor, not the SDK's tool runner, so the act owns its bounds and checks.
  - `internal/editor`: the Editor. Its acts (*reading an Item* into Facts, Claims and Entities; *placing a Fact*: an Item's Facts weighed against the Stories that share their Entities, becoming Developments or starting new Stories; and *connecting*: once placed, an Item's Facts weighed against the Facts near them, giving each Entity its role in a Fact and making cause Connections between Facts), each with its own instructions, output schema and checks, and the provider-neutral ports they call: `Model` (one call, at once) and `Batcher` (a provider's batch interface). The daily acts run in batches through `Batches`: an act is a `BatchAct` (what awaits it, each piece of work with its request and how its result is checked and written), so placing (`Editor.Placing()`) and connecting (`Editor.Connecting()`) plug in beside `Editor.Reading()`; one batch carries every act's requests, and the Claude adapter sends each to its act's model (`claude.Options.ActModels`). Placing holds back an Item that shares an Entity with an earlier Item awaiting placing until that one is placed, so batches thread Stories as placing one Item at a time would. After each Collection run, `Batches` applies the results of batches that have ended (matched by request ID), resubmits each failed request alone, and submits what awaits as one batch; pending batches are kept in the Record. Each piece of work gets `MaxAttempts` (3) attempts, and a batch not ended or not pollable by `BatchDeadline` (48h) counts one for each of its pieces; the attempts are kept with each batch's end (`work_attempts`), and work marked failed is left out of `ItemsToRead`, `FactsToPlace` and `FactsToConnect` by the storage adapter, listed on the Items page, and taken up again only by the `retry` admin command (below). A reading that fails its checks writes nothing and is tried again. Placing is shown past Feedback on Developments as precedent (`precedent.go`; the storage adapter's `PlacingPrecedents` selects at most eight, by shared Entity and Topic, then newest), as JSON lines after the act's instructions, and the precedents shown are kept with its result (`precedents_shown`). Reading is shown past *wrong* Feedback on Facts the same way (`ReadingPrecedents`: at most eight, by shared Topic alone, then newest; kept with act `reading`); its quote check still runs against the Item's text alone. `Editor.ReadWaiting` is the synchronous path, for when no batch interface is available (likewise `PlaceWaiting` and `ConnectWaiting`). `Editor.Reconnect(ctx, now)` re-runs connecting in real time over the Facts placed in the day before `now`; `main` passes it to the Briefing's `Schedule` as a `Before` step. Connections between Stories are derived by the storage adapter (`ConnectedStories`), never stored.
  - `internal/editor` keeps every model call reading and writing the Briefing make (`calls.go`), in a batch and through the synchronous path alike: a `Call` holds the act and work, the request as sent (a batch's request is kept when it is submitted, with the pending batch), the model asked for (`Deps.ModelFor`/`BatchDeps.ModelFor`, the adapter's `claude.Model.ModelFor`), the response as returned (`Response.Raw`, the provider's own form, beside its reported model, usage and stop reason; nil when none came), the outcome (`applied`, `refused` by the checks, or `failed`) with its reason, and `RequestHash`, the one hash of a request (instructions, schema, input, model) that recorded runs share. Applied calls go through `KeepCall`, failed attempts with their `WorkFailure` in `EndBatch`. The storage adapter keeps each distinct text once (`call_texts`) and refuses to rewrite or remove a kept call; `GET /calls/{id}` shows one with every attempt at its work, linked from each Fact on its Item's page and from failed work on the Items page, and records no open. No act is shown them. The Briefing's calls are keyed by its day (act `briefing`), each attempt kept, refused or failed ones before the failure, so its page links to the call that wrote it ("How it was written") or, on a day with none written, to each failed attempt; a Briefing written empty makes and keeps no call, and its page says so.
  - `internal/editor` also writes the Briefing, in real time (`briefing.go`, `schedule.go`): `Schedule` is its own clock in the app process, writing the day's Briefing at `BRIEFING_TIME` through `Model.Complete`, not the batch runner. Its `Before` steps run just before writing: the hook for connecting over the day's Facts. Each statement cites its Developments by ref, and the act's check refuses a Briefing with an untraced statement; a failure is kept, shown on the day's page, and retried after `RetryBriefing`.
  - `internal/editor` also writes the Sunday read (`sunday.go`, `sunday_tools.go`), the one act that is an agent with tools, through the provider-neutral `Conversation` port (`conversation.go`: one turn at a time, tool definitions, calls and results, the provider's own form of each turn passed back opaque as `Turn.Raw`). The act runs its own loop (bounded by `SundayReadMaxTurns` and `SundayReadTokenBudget`), its tools read the Record and Wikidata, and the agent submits through `submit_read`; the check refuses a statement citing nothing, or anything the run was not shown, and tells the agent why. `Schedule` writes it on Sundays just after the Briefing (`ScheduleDeps.SundayRead`), retried `RetrySundayRead` apart at most `SundayReadTries` times. Its page is `/sunday-reads/{day}`, linked from Sunday's Briefing; an Assessment's stable address is `/assessments/{id}`, and Feedback on the read (`new to me`, level `sunday read`) and its Assessments (`wrong`, `new to me`, level `assessment`) is given at `POST /sunday-reads/{day}/feedback`.
  - `internal/editor` also resolves a reading's Entities against Wikidata (`entities.go`, the `Wikidata` port) before it is written: matched Entities are Wikidata items, the rest the Editor's own, and the positions a matched person holds become Facts traced to the lookup.
  - `internal/wikidata`: the Wikidata adapter (Action API: `wbsearchentities`, `wbgetentities`), polite by Wikimedia's rules (go-slow's User-Agent, one request at a time a second apart, `maxlag`, `Retry-After` backoff). Tests fake it at HTTP with `wikidatatest.Handler`, serving real responses recorded once in `internal/wikidata/testdata/` (named by request; see the handler). Recording another is one `curl` with go-slow's User-Agent and a placeholder contact, never the Owner's.
  - `internal/polite`: the HTTP adapter Collection fetches through, carrying the politeness rules (User-Agent, conditional requests, one request per host at a time, `Retry-After` backoff, daily robots.txt).
  - `internal/sqlite`: the storage adapter, with its migrations.
  - `internal/server`: serving with graceful shutdown.

## Commands

- **Inner loop:** `go test ./...` (add `-run <Test>` or a package path to narrow it).
- **Full check:** `uvx --from pre-commit==4.7.0 pre-commit run --all-files`. It runs every hook below; CI runs exactly this. A `pre-commit` already on PATH works too, if it is at least 4.5.0. Install the git hook once per clone with `uvx --from pre-commit==4.7.0 pre-commit install`.
- **Re-record the Editor's recorded runs** (deliberately, when an act's instructions or schema change; it calls the real model once per fixture and costs money): `go test -count=1 ./internal/editor -run TestRecordedReadings -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `READING_MODEL` set in the environment; for placing, `-run TestRecordedPlacings -record` with `PLACING_MODEL` set; for connecting, `-run TestRecordedConnectings -record` with `CONNECTING_MODEL` set; for placing with a precedent (one call, on a hand-made Feedback fixture from `testdata/precedent/`), `-run TestRecordedPlacingPrecedent -record` with `PLACING_MODEL` set; for reading with a precedent (one call, on a hand-made *wrong* fixture on the Commons statement), `-run TestRecordedReadingPrecedent -record` with `READING_MODEL` set. Placing's recordings build on the recorded readings, placed in publication order, and connecting's on both, so re-record placing after re-recording any reading, and connecting after either. Target the package: other packages don't define `-record`. The responses land in `internal/editor/testdata/recorded/`; commit them, and the diff shows what changed. The suite only replays them and never calls a model. A fixture with no recording is skipped with a message naming this command. Fixtures (`internal/editor/testdata/govuk/`) come only from admissible Sources, with their licence attribution.
- **Re-record the Briefing** (after placing is re-recorded, or the act's instructions or schema change): `go test -count=1 ./internal/editor -run TestRecordedBriefing -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `BRIEFING_MODEL` set. It replays the recorded readings and placings into a Record with fixed Topics and Depths, and writes one Briefing (`testdata/recorded/briefing/`).
- **Re-record the Sunday read** (when the act's instructions, tools or checks change, or to bring it onto newer recordings of the earlier acts; it runs the agent on Claude Opus 5.5 and costs a few dollars): first copy `testdata/recorded/{reading,placing,connecting}` over `testdata/recorded/sunday/inputs/`, then `go test -count=1 ./internal/editor -run TestRecordedSundayRead -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `SUNDAY_READ_MODEL` set. It replays its own copies of the readings, placings and connectings (`sunday/inputs/`, so re-recording the earlier acts leaves its replay valid) into a Record with the Briefing's Topics, runs the whole conversation, and keeps every turn (`testdata/recorded/sunday/conversation.json`) with Wikidata's answers to its lookups (`testdata/recorded/sunday/wikidata/`, fetched with a placeholder contact), so the replay makes no network call.
- **Record commits for the register** (the quiet window, and Due on a change to the Editor): `git log --format='commit %H %cI' --name-only | docker compose run --rm -T app commits` (outside docker, pipe into `go run ./cmd/go-slow commits` with the same environment). The app can't see the repository, so commits are piped in; ones already kept are skipped, so pipe the whole log each time. An admin command of the binary, with the app's own config.
- **Retry failed work** (work that failed all its attempts, listed on the Items page): `docker compose run --rm app retry [reading|placing|connecting]` (outside docker, `go run ./cmd/go-slow retry ...`). It clears the failed marks on that act's work, or every act's with no act named, resetting the attempts, so the next Collection run submits it again. Admin commands live in `cmd/go-slow/admin.go`, tested end to end in `admin_test.go` and `backfill_test.go`.
- **Backfill Items' text** (one-off, for Items collected before their Source's text was fetched): `docker compose run --rm app backfill` (outside docker, `go run ./cmd/go-slow backfill`). It fetches, politely, the full text of every unread Item of a Source that declares a text fetch and has none, keeps it, and runs the Topic check over those Items again; Items already read are left as they were read. An Item whose fetch fails is logged and left for another run of the command.
- **Lint and format:** `go tool -modfile=tools/go.mod golangci-lint run ./...` and `... golangci-lint fmt`.
- **Run locally:** `cp .env.example .env`, then `docker compose up --build`, and open http://localhost:8080. The app logs JSON lines to stdout and stops cleanly on SIGTERM (`docker compose stop`). Outside docker: `go run ./cmd/go-slow` with the variables in `.env.example` set.

## Config

Only from environment variables, every one listed with a safe local value in `.env.example`, and all required: a missing one fails at start. The real `.env` is gitignored. Add a variable to `internal/config` and `.env.example` together. The model each act runs on is a variable (`READING_MODEL`, `PLACING_MODEL`, `BRIEFING_MODEL`, each a Claude model, since Claude is the one adapter); `BRIEFING_TIME` is when the Briefing is written and due by, `HH:MM` in `TZ`; `GOSLOW_ANTHROPIC_API_KEY` is a `config.Secret`, which never formats as its value. Never print, log or commit a real key.

## Go toolchain

- **Go is pinned by the `go` directive in `go.mod`** (1.27.3), the same in `tools/go.mod`. A local Go that is older downloads the pinned toolchain itself (`GOTOOLCHAIN=auto`, the default), CI's `actions/setup-go` reads `go.mod`, and the `Dockerfile`'s `golang:` tag repeats the version. Upgrade all four in one PR.
- **Tools are pinned in their own module**, `tools/go.mod` (`tool` directive), and run with `go tool -modfile=tools/go.mod <tool>`. A separate module keeps golangci-lint's hundreds of dependencies out of the app's `go.mod` and build. golangci-lint is at v2.14.0; its config is `.golangci.yml` (the `standard` linters plus a few for HTTP, SQL and errors; gofmt and goimports as formatters).
- **SQLite is `modernc.org/sqlite`**, pure Go, so the binary builds with `CGO_ENABLED=0` and runs on a distroless static image. Migrations are embedded SQL files in `internal/sqlite/migrations`, applied in name order by `sqlite.Open`, with the count applied kept in `PRAGMA user_version`. Never edit a migration that has been merged; add the next one. Migrations run on one connection with foreign keys off, each checked with `PRAGMA foreign_key_check` before it commits, so one can rebuild a table others refer to (SQLite can't change a `CHECK` in place): rename the old table with `PRAGMA legacy_alter_table = ON`, so other tables' references keep naming the original, create the new one, copy, drop the old (`0014_sunday_read.sql` rebuilds `feedback` this way).
- **htmx is vendored** at `internal/web/static/htmx-2.0.10.min.js`, byte-identical to the npm release (sha256 `71ea6718…c0de`), and excluded from the whitespace hooks so it stays so. Upgrading is replacing the file and the `<script>` in `templates/layout.html`. It stays on htmx 2.x while the Web apps Guide is written against it; htmx 4 is a separate decision.

## Checks and CI

- pre-commit hooks: the Global Guide's (`pre-commit-hooks`, actionlint, shellcheck), then `go mod tidy -diff` for both modules, `golangci-lint fmt`, `golangci-lint run` and `go test -race ./...`. The Go hooks are `language: system`, so they need `go` on PATH.
- CI is `.github/workflows/ci.yml`: one job, **`pre-commit`**, on every PR, and on pushes to `main` that change `go.mod`, `go.sum`, `tools/` pins or `.pre-commit-config.yaml`. **The required status check is `pre-commit`.** Renaming the job breaks merging once the `main` ruleset exists (it is created after CI first reports under this name).
- Actions and images are pinned to exact versions (the distroless base by digest).

## Known traps

- **Never name go-slow's key `ANTHROPIC_API_KEY`.** Claude Code reads that variable too: set in the shell `claude` is launched from, it switches Claude Code from the claude.ai login to the key, for its own requests and billing, and claude.ai connectors stop working. go-slow reads `GOSLOW_ANTHROPIC_API_KEY` instead, which agents inherit without Claude Code taking it. *Remove when:* never, while go-slow is built with Claude Code.
- actionlint shellchecks workflow `run:` steps only when `shellcheck` is on PATH. It is on GitHub's runners, not necessarily locally, so a local run can pass a step CI fails. *Remove when:* the actionlint hook brings its own shellcheck.
