# go-slow

A slow-news briefing: a Go web app, hypermedia-driven with htmx, storing the Record in SQLite.

There is no Go Guide yet; the Go tooling below is this repo's own until there is one. The Model calls Guide covers the Editor's acts; the system design's *The Editor* section is how go-slow applies it.

## Where things are

- [`CONTEXT.md`](CONTEXT.md): the domain language (Briefing, Owner, Story, Item...). Use its terms in code, tests and issues.
- [`docs/system-design/README.md`](docs/system-design/README.md): the design, its end state and hypotheses, and why it has its shape.
- [`docs/research/`](docs/research/): research that grounds the design.
- Code:
  - `cmd/go-slow`: `main`, the composition root. It alone reads the environment.
  - `internal/config`: the typed config.
  - `internal/web`: the web adapter and the app's constructor, `web.New`, with its templates, the vendored htmx and its one stylesheet (`static/go-slow.css`: plain CSS, dark and minimal, linked from the layout; its quiet style, the class `quiet`, is for whatever should recede; its status hues, `status` with `status-supported`, `status-refuted`, `status-undecided` or `status-due`, are for a verdict, the register's statuses and the same family for a call's outcomes, as its header says). The reading pages (the Briefing, the Sunday read) are body and margin (below), folded at rest. The Briefing reads as its Stories' titles and statements, each statement a block whose margin holds each Development it cites (its Fact, linking the Development on its Story's Timeline, and its Item as a `.citation` at the Fact on the Item's page). The Sunday read's title carries its *New to me*; its statements are blocks as on the Briefing, its Assessments blocks under their own heading, set apart by a left rule (`.assessment`; withdrawn, struck through and `quiet`), their margin what each rests on, what it supersedes and the machine label `reached · turn N` (view model `reached`, linking the turn); the Stories it started are a `quiet` list at the end. On these pages Feedback is the frequent act, so a block's Feedback controls (`.actions` groups: a Briefing statement's one per Development it cites, labelled by its Fact, shortened; an Assessment's Wrong and New to me) sit in its `.block-body`, not its margin, which folds away; a title's (a Story's heading, the read's title) in its `.title-row`. They are hidden at rest by a visually-hidden rule that keeps them in the tab order, and shown on `:hover`/`:focus-within` of the block or row, folded or open; Feedback already given (`gives.Given`) shows at rest outside them. **Body and margin** is the layout every page showing the Editor's work shares (an Item's page and the reading pages so far; each other page adopts it in its own change): each block (`<li class="block">` in a `<ul class="blocks">`) has its text in `.block-body` and its notes in `.block-margin` beside it (the quote, `quiet`; a date only where it differs from the Item's; Entity pills; the machine label; on an inspect page, the block's Feedback `.actions`, revealed on hover and focus), and on a narrow window the notes drop below. The blocks sit in one `<div class="margined" data-margin="open|folded">` holding the one fold control, `{{template "margin-fold" "open|folded"}}`: an inspect page (an Item, a Story) starts open, a reading page (the Briefing, the Sunday read) folded. The state lives only in `data-margin`, toggled by `static/margin-fold.js` (plain JS, loaded by the layout, a click listener on `document` and its button's `aria-expanded` synced on `htmx:load`), so nothing is remembered across pages. Its visual vocabulary, one meaning per shape, is in classes documented in the stylesheet beside `quiet`: an Entity is a `.pill` (its name, then its Role or else its kind in a `.pill-tag`, in one hue, `--entity`, teal, apart from the link accent and every status hue; view model `pill`, built by `pillsInvolved` and `pillMentioned`, rendered by `{{template "pills"}}`/`{{template "pill"}}`), an Item a `.citation` (its Source's name where the page has it, then its title in `<cite>`, a link; view model `itemCitation`, `{{template "citation"}}`), and how something was made a `.machine` label worded `<act> · call N` (view model `made`, `{{template "made"}}`). The pieces live in `margin.go` and `templates/margin.html`, which `page` parses into every page. Every full page carries the layout's one navigation, a flat row reaching each index (`indexes` in `web.go`); each page template declares which index it is, if any (`page(index, ...)`), and that link is marked `aria-current="page"`; pages link at their top only to their own context (a trail's Briefing, a call's work), never repeating the navigation. It logs each request it answers as one line (`request_log.go`: method, path without its query, status, `duration_ms`; never form values), through the `Log` it is given; a `5xx` is logged at error level with the error `serverError` noted on the request, and static files at debug level, so a page load is one info line. A request htmx doesn't swap (any `4xx` but `422`, any `5xx`, or no answer) is shown in the layout's `#request-errors` region by `static/request-errors.js`, plain JS with no build step, and cleared by the next request that succeeds.
  - `internal/collect`: Collection, the Sources list with each one's terms (licence, attribution, what may be kept) and rate limit, reading each feed format (Atom, the ONS release search, Parliament's written statements) and the *No Source goes quiet* check, with its ports (`Fetcher`, `Store`). A Source whose feed carries only a summary declares how each entry's full text is fetched (`Source.Text`, `text.go`: GOV.UK's Content API document for the entry's path, or the written statement itself), and a new entry is kept only once its text is fetched, through the same `Fetcher`; one whose fetch fails is left out, and the feed's validators are not saved, so the next run sees it again. `Backfill` (`backfill.go`, its port `TextStore`) gives the text to unread Items collected with only a summary. Its timetable runs inside the app process, started by `main`.
  - `internal/interest`: the Owner's Topics and Depths, and the lazy-reading check that ties Items to Topics with no model call. Collection runs the check after every run; taking up a Topic, or changing its Depth, re-runs it for that Topic over the Items not yet read.
  - `internal/feedback`: the Owner's Feedback. `Service.Give` validates which kinds each level takes, keeps the piece as given (with its Depth and when), and applies its `Effect` (worked out by `EffectOf` from the piece alone, so a changed mechanism can be re-run over all of it), in one transaction through its `Store` port. Effects are marks naming the Feedback (`withdrawn_by`, `unwanted_by`, `missed_by`), never deletions; the storage adapter keeps withdrawn records out of every act's queries. Given inline on the Briefing (`POST /briefings/{day}/feedback`) and a Story's page (`POST /stories/{id}/feedback`), each answering `303` back to its page or `422` with the page re-rendered around the failed form; where Feedback of a kind already stands on a target, that target's button renders as given, beside the Undo of that piece from the page (the web adapter matches the page's buttons against the kept Feedback, `givenIn`), and is not offered again; `GET /feedback` lists it all as given, each piece linked to the calls behind what it is about (worked out in the storage adapter's kept-Feedback query by the same lookups as the Item and Story pages), or saying the Owner made it. `Service.Undo` marks a piece undone (`undone_at`, kept, never deleted) and the storage adapter's `lift` works each mark it made out again from the Feedback still standing (the earliest standing piece that makes it, or none), so a mark another piece makes stays; what an undone *missed* added is withdrawn by it and shown nowhere. Undone from each page that lists it (`PUT {page}/feedback/{id}/undone` on the Briefing, a Story's page, a Sunday read, and `PUT /feedback/{id}/undone`), answering `303` back. Undone Feedback is never precedent and the register does not count it.
  - `internal/register`: the register. Each hypothesis of the end state read from the Record by its declared reading rule (windows counted from the first Briefing), pure code over a constructed `register.Record`, shown at `/register`. Status lives only here, derived on every view, never stored. Opening a Briefing or a Sunday read is kept as a side record, once per day; commits come from the `commits` admin command (below), which also marks the commits that change the Editor (`internal/editor`, `internal/claude`, `internal/feedback`, `internal/sqlite/feedback.go`).
  - `internal/claude`: the Claude model adapter (Anthropic's Messages API and Message Batches API through `anthropic-sdk-go`, structured output against the act's schema). Anthropic's types stay inside it. Its `Turn` (the `Conversation` port) uses the beta Messages API for strict tools, adaptive thinking at high effort, `fallbacks: "default"` on a refusal and prompt caching; a manual loop in the Editor, not the SDK's tool runner, so the act owns its bounds and checks.
  - `internal/editor`: the Editor. Its acts (*reading an Item* into Facts and Claims, and the Entities the Item mentions, given once; *placing a Fact*: an Item's Facts weighed against the Item's candidate Stories (the storage adapter's `CandidateStories`: those whose Items mention an Entity the Item mentions, at most 20, ranked by the Entities each shares weighted by rarity over Stories, then by newest Development, each with what it shares), becoming Developments or starting new Stories; and *connecting*: once placed, an Item's Facts weighed against the Facts near them (`FactsNear`: at most 30 whose Items mention an Entity the Item mentions or that are Developments in one of their Stories, nearest in date first), deciding which of the Entities the Item mentions (`ToConnect.Mentions`, shown once with their kinds, never reading's per-Fact lists) each Fact involves, each in its Role (actor, undergoer, place, occasion), and making cause Connections between Facts; connecting a Fact again replaces its roles), each with its own instructions, output schema and checks, and the provider-neutral ports they call: `Model` (one call, at once) and `Batcher` (a provider's batch interface). The daily acts run in batches through `Batches`: an act is a `BatchAct` (what awaits it, each piece of work with its request and how its result is checked and written), so placing (`Editor.Placing()`) and connecting (`Editor.Connecting()`) plug in beside `Editor.Reading()`; one batch carries every act's requests, and the Claude adapter sends each to its act's model (`claude.Options.ActModels`). Placing holds back an Item that mentions an Entity an earlier Item awaiting placing mentions until that one is placed, so batches thread Stories as placing one Item at a time would. After each Collection run, `Batches` applies the results of batches that have ended (matched by request ID), resubmits each failed request alone, and submits what awaits as one batch; pending batches are kept in the Record. Each piece of work gets `MaxAttempts` (3) attempts, and a batch not ended or not pollable by `BatchDeadline` (48h) counts one for each of its pieces; the attempts are kept with each batch's end (`work_attempts`), and work marked failed is left out of `ItemsToRead`, `FactsToPlace` and `FactsToConnect` by the storage adapter, listed on the Items page, and taken up again only by the `retry` admin command (below). A reading that fails its checks writes nothing and is tried again. Placing is shown past Feedback on Developments as precedent (`precedent.go`; the storage adapter's `PlacingPrecedents` selects at most eight, by shared Entity and Topic, then newest), as JSON lines after the act's instructions, and the precedents shown are kept with its result (`precedents_shown`). Reading is shown past *wrong* Feedback on Facts the same way (`ReadingPrecedents`: at most eight, by shared Topic alone, then newest; kept with act `reading`); its quote check still runs against the Item's text alone. `Editor.ReadWaiting` is the synchronous path, for when no batch interface is available (likewise `PlaceWaiting` and `ConnectWaiting`). `Editor.Reconnect(ctx, now)` re-runs connecting in real time over the Facts placed in the day before `now`; `main` passes it to the Briefing's `Schedule` as a `Before` step. Connections between Stories are derived by the storage adapter (`ConnectedStories`), never stored.
  - `internal/editor` keeps every model call reading, placing, connecting and writing the Briefing make (`calls.go`), in a batch and through the synchronous paths alike (`Editor.callNow`; `Reconnect` included): a `Call` holds the act and work, the request as sent (a batch's request is kept when it is submitted, with the pending batch), the model asked for (`Deps.ModelFor`/`BatchDeps.ModelFor`, the adapter's `claude.Model.ModelFor`), the response as returned (`Response.Raw`, the provider's own form, beside its reported model, usage and stop reason; nil when none came), the outcome (`applied`, `refused` by the checks, or `failed`) with its reason, and `RequestHash`, the one hash of a request (instructions, schema, input, model) that recorded runs share. Applied calls go through `KeepCall`, failed attempts with their `WorkFailure` in `EndBatch`. The storage adapter keeps each distinct text once (`call_texts`) and refuses to rewrite or remove a kept call; `GET /calls/{id}` shows one with every attempt at its work, linked from each Fact and Claim on its Item's page (the machine label "read · call N"), from each Development and cause Connection on a Story's page ("How it was placed", "How it was connected") and from failed work on the Items page, and records no open. The storage adapter finds a Development's call by its Item and the time it was placed, and a Connection's by the Item it was made on (`fact_connections.made_on`) and the time it was made; a Development the Owner added has none. No act is shown them. The Briefing's calls are keyed by its day (act `briefing`), each attempt kept, refused or failed ones before the failure, so a written Briefing links to its trail ("How this was written", `GET /briefings/{day}/trail`: the call that wrote it, then the placing and reading calls behind each Development it cites as written, from the storage adapter's `BriefingCitations`, with tokens per call and summed over the distinct calls; it records no open) and a day with none written to each failed attempt; a Briefing written empty makes and keeps no call, and its page says so.
  - `internal/editor` also writes the Briefing, in real time (`briefing.go`, `schedule.go`): `Schedule` is its own clock in the app process, writing the day's Briefing at `BRIEFING_TIME` through `Model.Complete`, not the batch runner. Past `BRIEFING_TIME` it waits until no work on Items collected before it began waiting awaits an act (the storage adapter's `WorkAwaiting`), at most `BriefingWait`; `main` starts it only once the start's first Collection run has ended. While it waits, the day's page polls `GET /briefings/{day}/status`, a fragment that re-polls only while the Briefing is being written. Its `Before` steps run just before writing: the hook for connecting over the day's Facts. Each statement cites its Developments by ref, and the act's check refuses a Briefing with an untraced statement; a failure is kept, shown on the day's page, and retried after `RetryBriefing`.
  - `internal/editor` also writes the Sunday read (`sunday.go`, `sunday_tools.go`), the one act that is an agent with tools, through the provider-neutral `Conversation` port (`conversation.go`: one turn at a time, tool definitions, calls and results, the provider's own form of each turn passed back opaque as `Turn.Raw`). The act runs its own loop (bounded by `SundayReadMaxTurns` and `SundayReadTokenBudget`), its tools read the Record and Wikidata, and the agent submits through `submit_read`; the check refuses a statement citing nothing, or anything the run was not shown, and tells the agent why. `Schedule` writes it on Sundays just after the Briefing (`ScheduleDeps.SundayRead`), retried `RetrySundayRead` apart at most `SundayReadTries` times. Each attempt's conversation is kept turn by turn (`editor.KeptConversation`, with the read or its failure, in one transaction): each turn keeps only the messages new with its request (the conversation's prefix isn't kept again), the turn as returned (a refusal's too), its usage and what came of it (`continued`, `applied`, `refused` with the reason told back, `failed`), and `editor.ConversationRequestHash` of the whole request, the conversation counterpart of `RequestHash`. The conversation's page is `/conversations/{id}`, turn by turn (`#turn-N`) with tokens per turn and summed, and is the read's trail ("How this was written"), linked from the read, its failure and each Assessment (the submitting turn). The read's page is `/sunday-reads/{day}`, linked from Sunday's Briefing; an Assessment's stable address is `/assessments/{id}`, and Feedback on the read (`new to me`, level `sunday read`) and its Assessments (`wrong`, `new to me`, level `assessment`) is given at `POST /sunday-reads/{day}/feedback`.
  - `internal/editor` also resolves a reading's Entities (the Item's mentions) against Wikidata (`entities.go`, the `Wikidata` port) before it is written: matched Entities are Wikidata items, the rest the Editor's own, and the positions a matched person holds become Facts traced to the lookup. The Record keeps the mentions (`item_mentions`), which connecting is shown and by which placing, connecting and the missed-Development form find work. A reading ties no Entity to its Facts or Claims: a Fact is tied to an Entity only by the Role connecting gives it (`fact_entities`, role required). `editor.Fact.Entities` is set only on a Reference Fact (the Entity it was looked up for, `reference_fact_entities`); a Fact drawn from an Item carries none, and what needs its Item's mentions reads them from the Item (`ToPlace.Mentions`, `ToConnect.Mentions`, `ReadItem.Mentions`), or the Entities it involves from `Fact.Involves`. Reading refuses an answer in its earlier schema (Entities with each Fact and Claim, no mentions).
  - `internal/wikidata`: the Wikidata adapter (Action API: `wbsearchentities`, `wbgetentities`), polite by Wikimedia's rules (go-slow's User-Agent, one request at a time a second apart, `maxlag`, `Retry-After` backoff; a lookup answered `maxlag` is sent once more after the backoff, nothing else is retried). Tests fake it at HTTP with `wikidatatest.Handler`, serving real responses recorded once in `internal/wikidata/testdata/` (named by request; see the handler). Recording another is one `curl` with go-slow's User-Agent and a placeholder contact, never the Owner's.
  - `internal/polite`: the HTTP adapter Collection fetches through, carrying the politeness rules (User-Agent, conditional requests, one request per host at a time, `Retry-After` backoff, daily robots.txt).
  - `internal/sqlite`: the storage adapter, with its migrations.
  - `internal/server`: serving with graceful shutdown.

## Commands

- **Inner loop:** `go test ./...` (add `-run <Test>` or a package path to narrow it).
- **Full check:** `uvx --from pre-commit==4.7.0 pre-commit run --all-files`. It runs every hook below; CI runs exactly this. A `pre-commit` already on PATH works too, if it is at least 4.5.0. Install the git hook once per clone with `uvx --from pre-commit==4.7.0 pre-commit install`.
- **Re-record the Editor's recorded runs** (deliberately, when an act's instructions, schema or model change; it calls the real model five times per fixture, more where the checks refuse an attempt, and costs money): `go test -count=1 -timeout 90m ./internal/editor -run TestRecordedReadings -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `READING_MODEL` set in the environment (the default 10m test timeout is too short for five samples of every fixture); for placing, `-run TestRecordedPlacings -record` with `PLACING_MODEL` set; for connecting, `-run TestRecordedConnectings -record` with `CONNECTING_MODEL` set; for placing with a precedent (on a hand-made Feedback fixture from `testdata/precedent/`), `-run TestRecordedPlacingPrecedent -record` with `PLACING_MODEL` set; for reading with a precedent (on a hand-made *wrong* fixture on the Commons statement), `-run TestRecordedReadingPrecedent -record` with `READING_MODEL` set. **A recording is samples, judged by a rule** (system design: *A recording is one sample, and a property is judged by its pass rate*): each fixture is sampled 5 times (the rule is `dailyRule` in `recorded_samples_test.go`; the Sunday read takes 3, `sundayReadRule`, below), each sample run as in use, up to `editor.MaxAttempts` attempts against the act's checks, and kept at `testdata/recorded/<act>/<fixture>/<k>.json` (the last attempt, with the refused ones before it under `earlier_attempts`), written attempt by attempt as it arrives. The suite replays every sample and judges each property per fixture: *passes its checks within its attempts* over all 5 samples, each test-only property over the samples that passed; supported at 5 of 5, refuted at 3 or fewer, undecided at 4. Refuted or undecided fails the test, as does a fixture with fewer samples than the rule, or samples answering different requests. An undecided fixture is read again on 5 fresh samples, judged alone: delete its directory and record again (`-record` keeps the samples already kept for the request the act sends now, so it also resumes a stopped recording, and draws only what is missing or stale). Don't add samples to push a count over the line, and don't change a check or property to pass. For placing and connecting, whose fixtures build on each other, each sample of a fixture runs over the Record the fixtures before it left, each carried on by its first sample to pass, so a fresh reading of one fixture makes the later fixtures' samples stale and `-record` redraws them. Each act is replayed over its own frozen copies of the recordings it rests on, under `testdata/recorded/<act>/inputs/<upstream act>/` (placing over readings, connecting over readings and placings, the Briefing and the Sunday read over all three, placing with a precedent over the reaction's reading), never over the upstream recordings themselves, so re-recording one act leaves every other act valid: re-record only the act you changed. Target the package: other packages don't define `-record`. The responses land in `internal/editor/testdata/recorded/`; commit them, and the diff shows what changed. The suite only replays them and never calls a model. Each recording keeps the hash of the request it answered (`editor.RequestHash`, with the model the act is pinned to in `.env.example`), and a replay whose act now builds another request (changed instructions, schema, input or pin) fails as stale, naming the command that re-records it; an act's frozen copies of upstream recordings are replayed unchecked, since the act that made them checks them. A fixture with no samples fails with a message naming this command. Fixtures (`internal/editor/testdata/govuk/`) come only from admissible Sources, with their licence attribution.
- **Re-record the Briefing** (when the act's instructions or schema change): `go test -count=1 ./internal/editor -run TestRecordedBriefing -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `BRIEFING_MODEL` set. It replays its own copies of the readings, placings and connectings (`testdata/recorded/briefing/inputs/`) into a Record with fixed Topics and Depths, and writes the day's Briefing, sampled 5 times by the rule above (`testdata/recorded/briefing/saturday/`).
- **Refresh an act's frozen copies** (to bring a downstream act onto an upstream act's newer recordings): its own change, never part of the change to the upstream act, made once that act's new behaviour is accepted on its own recordings. Copy every upstream act's current recordings together over the act's `inputs/`: a frozen copy is the fixture's first sample, copied as it is (for connecting, each `testdata/recorded/reading/<fixture>/1.json` to `connecting/inputs/reading/<fixture>.json` and each `testdata/recorded/placing/<fixture>/1.json` to `connecting/inputs/placing/<fixture>.json`), and only from recordings whose every property is supported, so the first sample's last attempt is the one that passed. Then re-record that act alone. Never copy one upstream act without the others: new readings with old placings is a run no Editor makes. Refresh the Sunday read only on the Owner's say, since it costs dollars. Until a refresh, two checks cover the gap, with no recording of their own: the chain replay (`TestRecordedChainTracesEveryBriefingStatementToAQuote`, over the Briefing's copies and each of its samples that passes) and the compatibility check (`TestEachActsCurrentRecordingsAreTakenByTheActsDownstream`: each act's current recordings, each fixture's first sample, over its own copies, fed through every act downstream on a fake model). Each downstream act's own recorded test replays over its own directory copied alone (`ownDirectory`; `TestEachRecordedActReplaysOverItsOwnInputsAlone` does so for the Sunday read), so an act that reads another's recordings fails. The recorded tests run in parallel (`t.Parallel`): with five samples per fixture, `go test -race ./internal/editor` takes about 75s.
- **Re-record the Sunday read** (only on the Owner's say: when the act's instructions, tools or checks change, or as a refresh onto newer recordings of the earlier acts; it runs the agent on Claude Opus 5.5 three times and costs about a dollar): for a refresh, first copy each fixture's first sample of `testdata/recorded/{reading,placing,connecting}` together over `testdata/recorded/sunday/inputs/{reading,placing,connecting}/` (`reading/<fixture>/1.json` to `sunday/inputs/reading/<fixture>.json`, and so on), in its own commit, then `go test -count=1 -timeout 90m ./internal/editor -run '^TestRecordedSundayRead$' -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `SUNDAY_READ_MODEL` set (`-max-tries N` bounds each sample's tries below the act's own `SundayReadTries`, to keep a run within the retries its brief allows). It takes **3 samples** (`sundayReadRule`: every property supported at 3 of 3, refuted at 1 or none, undecided at 2, which is read again on 3 fresh samples, judged alone: delete `sunday/<k>/` and record again). Each sample runs as in use, up to `SundayReadTries` tries, each a whole conversation over a fresh copy of a Record built from its own copies of the readings, placings and connectings (`sunday/inputs/`, so re-recording the earlier acts leaves its replay valid) with the Briefing's Topics. Each try is kept as it runs, turn by turn, at `testdata/recorded/sunday/<k>/try-<n>/conversation.json` (every turn in the provider's own form, with `editor.ConversationRequestHash` of its request, the hash a kept turn carries), with Wikidata's answers to its lookups beside it (`wikidata/`, fetched with a placeholder contact), so the replay makes no network call. A turn whose request the act no longer sends fails the replay as stale; `-record` keeps the tries that still replay and draws afresh a stale one or one left unfinished.
- **Report each act's yield on every re-recording above, and paste the table into the PR body**: extract the recordings being replaced (e.g. `git archive -o <scratch>/old.tar origin/main internal/editor/testdata/recorded`, then `tar -xf <scratch>/old.tar -C <scratch>/old`), then `go run ./internal/editor/yield <scratch>/old/internal/editor/testdata/recorded internal/editor/testdata/recorded`. It prints, per act and per fixture, before → after: Facts, Claims and distinct Entities for reading, and its Facts worded as a future act (*will* as the auxiliary, *would*, *set to*, *expected to*, *is to*: counted, never judged, since "is set to be built" words a present arrangement, which is a Fact); Developments and new Stories for placing; Connections for connecting, and what it leaves out, which its checks can't see: the mentions it was shown (those of its frozen copy of the fixture's reading, `connecting/inputs/reading/<fixture>.json`, matched by name) that it involves in no Fact, and the Facts it gives no Roles (both counted, never judged); statements and Stories for the Briefing, with totals, and marks fixtures added or removed. A fixture's samples show as the range they drew, least–most, each by its last attempt, and a total as the range from every fixture's least to its most. Its last table, *agreement*, is how alike each fixture's samples are in what each Fact involves (the mean pairwise Jaccard index of each Fact's set, over every pair of samples and every Fact, and a mean over the fixtures): for connecting by Entity and Role and by Entity alone, and for the same fixtures' readings by each Fact's list of Entities, pairing a Fact with the other sample's statement sharing the most of its words, at least half. It reports and never fails: whether a shift is a loss is a reading. It calls no model, counts nothing in `inputs/` (frozen copies of upstream recordings; connecting's are read only for the mentions it was shown) and acts it doesn't count (the Sunday read), and is a dev tool under `internal/`, not part of the app binary.
- **Record commits for the register** (the quiet window, and Due on a change to the Editor): `git log --format='commit %H %cI' --name-only | docker compose run --rm -T app commits` (outside docker, pipe into `go run ./cmd/go-slow commits` with the same environment). The app can't see the repository, so commits are piped in; ones already kept are skipped, so pipe the whole log each time. An admin command of the binary, with the app's own config.
- **Retry failed work** (work that failed all its attempts, listed on the Items page): `docker compose run --rm app retry [reading|placing|connecting]` (outside docker, `go run ./cmd/go-slow retry ...`). It clears the failed marks on that act's work, or every act's with no act named, resetting the attempts, so the next Collection run submits it again. Admin commands live in `cmd/go-slow/admin.go`, tested end to end in `admin_test.go` and `backfill_test.go`.
- **Backfill Items' text** (one-off, for Items collected before their Source's text was fetched): `docker compose run --rm app backfill` (outside docker, `go run ./cmd/go-slow backfill`). It fetches, politely, the full text of every unread Item of a Source that declares a text fetch and has none, keeps it, and runs the Topic check over those Items again; Items already read are left as they were read. An Item whose fetch fails is logged and left for another run of the command.
- **Lint and format:** `go tool -modfile=tools/go.mod golangci-lint run ./...` and `... golangci-lint fmt`.
- **Run locally:** `cp .env.example .env`, then `docker compose up --build`, and open http://localhost:8080 (the port is published on `127.0.0.1` only; the Record is the host folder `RECORD_DIR`, bind-mounted). For daily use, see the *Runbook* below. The app logs JSON lines to stdout and stops cleanly on SIGTERM (`docker compose stop`). Outside docker: `go run ./cmd/go-slow` with the variables in `.env.example` set.

## Runbook: go-slow on the laptop

go-slow runs on the Owner's laptop, from this repo's image and `docker-compose.yml`, published on `127.0.0.1` only (system design: *go-slow runs when the Owner starts it*). Nothing keeps it running: start it each day to read.

- **Docker without Docker Desktop:** the containers run in Colima, which needs no login. Once: `brew install colima docker docker-compose`, add `"cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"]` to `~/.docker/config.json` so `docker compose` finds the plugin, then `colima start --memory 4 --cpu 4` (it switches the docker context to `colima`, and later starts keep the size). The VM needs the 4 GiB: compiling `anthropic-sdk-go`, one 120k-line generated package, peaks at about 1.4 GB in one compiler process, and Colima's default 2 GiB VM kills the image build.
- **Once:** `cp .env.example .env`, set your own `COLLECTION_CONTACT` and `GOSLOW_ANTHROPIC_API_KEY`, and set `RECORD_DIR` to an absolute path outside the repo (the folder holding the Record; `mkdir -p` it). Copying that folder while go-slow is stopped is a backup.
- **Start each day:** `colima start` (if it isn't running; `colima status` says), `docker compose up -d`, then open http://localhost:8080. The start's Collection run fetches what came in overnight and submits it in batches; past `BRIEFING_TIME` the page says the Briefing is being written and shows it once the work is done (at most `editor.BriefingWait`).
- **Stop:** `docker compose stop` (SIGTERM; the app drains and exits). `docker compose logs app` shows its JSON log.
- **Upgrade:** `git switch main`, `git pull`, then `docker compose up --build -d`. Migrations run on start.
- **Record commits for the register:** `git log --format='commit %H %cI' --name-only | docker compose run --rm -T app commits` (see *Commands*). Pipe the whole log each time.

**An agent starts the day's run when it notices it hasn't been done** (the Owner's standing say, 2026-10-27): if `docker compose ps` shows no app running on a day of work, the orchestrating agent runs *Start each day* (rebuilding with `--build` when `main` has moved since the image was built) and tells the Owner. That is the one way an agent touches the Record: never a sub-agent, never `docker compose run` of an admin command, a migration by hand or a copy, move or edit of `RECORD_DIR`, without the Owner's say for that act. The Record is the Owner's.

`COLLECTION_CONTACT` is still the example placeholder, on the Owner's call while go-slow's volume is low (2026-10-27); a real contact goes in before it fetches much more.

## Config

Only from environment variables, every one listed with a safe local value in `.env.example`, and all required: a missing one fails at start. The real `.env` is gitignored. Add a variable to `internal/config` and `.env.example` together. The model each act runs on is a variable (`READING_MODEL`, `PLACING_MODEL`, `CONNECTING_MODEL`, `BRIEFING_MODEL`, `SUNDAY_READ_MODEL`, each a Claude model, since Claude is the one adapter), always a pinned model ID, never an alias the provider can move (`claude-haiku-5-5` and `claude-opus-5-5` are fixed snapshots; how that was checked is in [`docs/research/models.md`](docs/research/models.md)). **A model change is a re-record, like an instructions change**: the model is part of the act's request, so re-record that act's recordings on the new model (*Commands*, above) in the same change. Each result keeps the model the provider reports, not the one configured; `BRIEFING_TIME` is when the Briefing is written and due by, `HH:MM` in `TZ`; `GOSLOW_ANTHROPIC_API_KEY` is a `config.Secret`, which never formats as its value. Never print, log or commit a real key.

## Go toolchain

- **Go is pinned by the `go` directive in `go.mod`** (1.27.3), the same in `tools/go.mod`. A local Go that is older downloads the pinned toolchain itself (`GOTOOLCHAIN=auto`, the default), CI's `actions/setup-go` reads `go.mod`, and the `Dockerfile`'s `golang:` tag repeats the version. Upgrade all four in one PR.
- **Tools are pinned in their own module**, `tools/go.mod` (`tool` directive), and run with `go tool -modfile=tools/go.mod <tool>`. A separate module keeps golangci-lint's hundreds of dependencies out of the app's `go.mod` and build. golangci-lint is at v2.14.0; its config is `.golangci.yml` (the `standard` linters plus a few for HTTP, SQL and errors; gofmt and goimports as formatters).
- **SQLite is `modernc.org/sqlite`**, pure Go, so the binary builds with `CGO_ENABLED=0` and runs on a distroless static image. Migrations are embedded SQL files in `internal/sqlite/migrations`, applied in name order by `sqlite.Open`, with the count applied kept in `PRAGMA user_version`. Never edit a migration that has been merged; add the next one. Migrations run on one connection with foreign keys off, each checked with `PRAGMA foreign_key_check` before it commits, so one can rebuild a table others refer to by SQLite's procedure (Web apps Guide, *Storage*: create `new_X`, copy, drop `X`, rename `new_X` to `X`). `0014_sunday_read.sql` rebuilt `feedback` in the other order (renaming the old table first, under `PRAGMA legacy_alter_table = ON`); it is merged, so it stays, but the next rebuild follows SQLite's order.
- **htmx is vendored** at `internal/web/static/htmx-2.0.10.min.js`, byte-identical to the npm release (sha256 `71ea6718…c0de`), and excluded from the whitespace hooks so it stays so. Upgrading is replacing the file and the `<script>` in `templates/layout.html`.

## Checks and CI

- pre-commit hooks: the Global Guide's (`pre-commit-hooks`, actionlint, shellcheck; actionlint comes from `actionlint-py`, with `shellcheck-py` in its `additional_dependencies` for the shellcheck on its PATH, as the Rust Guide does), then `go mod tidy -diff` for both modules, `golangci-lint fmt`, `golangci-lint run` and `go test -race ./...`. The Go hooks are `language: system`, so they need `go` on PATH.
- CI is `.github/workflows/ci.yml`: one job, **`pre-commit`**, on every PR, and on pushes to `main` that change `go.mod`, `go.sum`, `tools/` pins or `.pre-commit-config.yaml`. **The required status check is `pre-commit`.** Renaming the job breaks merging once the `main` ruleset exists (it is created after CI first reports under this name).
- Actions and images are pinned to exact versions (the distroless base by digest).

## Known traps

- **Never name go-slow's key `ANTHROPIC_API_KEY`.** Claude Code reads that variable too: set in the shell `claude` is launched from, it switches Claude Code from the claude.ai login to the key, for its own requests and billing, and claude.ai connectors stop working. go-slow reads `GOSLOW_ANTHROPIC_API_KEY` instead, which agents inherit without Claude Code taking it. *Remove when:* never, while go-slow is built with Claude Code.
