# go-slow

A slow-news briefing: a Go web app, hypermedia-driven with htmx, storing the Record in SQLite.

**Deviation from the Web apps Guide:** the Guide's lightweight CQRS says "not event sourcing"; go-slow's **Record** is event-based (system design: *The Record as events*), because it is a record of judgements, each kept with its judge, and views choose whose judgements they read and as at when. **Sources** and **Topics** stay plain records. The code below still describes the Record before it became events, until the slices of #208 land.

There is no Go Guide yet; the Go tooling below is this repo's own until there is one. The Model calls Guide covers the Editor's acts; the system design's *The Editor* section is how go-slow applies it.

  - `internal/config`: the typed config.
  - `internal/web`: the web adapter and the app's constructor, `web.New`, with its templates, the vendored htmx and its one stylesheet (`static/go-slow.css`: plain CSS, dark and minimal, linked from the layout; its quiet style, the class `quiet`, is for whatever should recede; its status hues, `status` with `status-supported`, `status-refuted`, `status-undecided` or `status-due`, are for a verdict, the register's statuses and the same family for a call's outcomes, as its header says). The Briefing looks as a Story's page does: body and margin (below), margin open. It reads as its Stories, each a title block (the title, linking the Story, in the body; its Unwanted and New to me and the Feedback already given in the margin) and its statements, each a block whose margin holds each Development it cites (its Fact, linking the Development on its Story's Timeline, and its Item as a `.citation` at the Fact on the Item's page), then the Feedback already given on each, then its Feedback `.actions` groups, one per Development it cites, labelled by its Fact, shortened; as on a Story's page they are revealed on hover and focus and fold away with the margin. The Sunday read, the one reading page, is body and margin folded at rest. Its title carries its *New to me*; its statements are blocks as on the Briefing, its Assessments blocks under their own heading, set apart by a left rule (`.assessment`; withdrawn, struck through and `quiet`), their margin what each rests on, what it supersedes and the machine label `reached · turn N` (view model `reached`, linking the turn); the Stories it started are a `quiet` list at the end. On it Feedback is the frequent act, so an Assessment's Feedback controls (`.actions`: Wrong and New to me) sit in its `.block-body`, not its margin, which folds away; the read's title's in its `.title-row`. They are hidden at rest by a visually-hidden rule that keeps them in the tab order, and shown on `:hover`/`:focus-within` of the block or row, folded or open; Feedback already given (`gives.Given`) shows at rest outside them. The Topics page is a table of the Followed Topics: each row's Depth a segmented control (`.segmented`, a button per Depth in the row's `PUT` form, the current one `aria-pressed`) that saves on click, Remove in the row's `.actions`, hidden at rest the same way and shown on the row's `:hover`/`:focus-within`, and Take up a Topic a `<details>` above it, open again when a take-up fails. The Items page leads with exceptions only when there are any (quiet Sources, and failed work with its `retry` command, `status-refuted` for failed), otherwise one quiet line over the folded Sources; its collected Items are body-and-margin blocks, margin open, each Item's status a `.machine` label (`itemRow.Status`: the pipeline's own wording, not prose: `read · N names, N speakers, N rejected`, `awaiting reading`, `awaiting cutting` or `no text yet`, whatever Topics it touches), and Upcoming folds at its foot. **Body and margin** is the layout every page showing the Editor's work shares (an Item's page, a Story's, the Briefing, the Sunday read and a conversation's so far; each other page adopts it in its own change): each block (`<li class="block">` in a `<ul class="blocks">`) has its text in `.block-body` and its notes in `.block-margin` beside it (the quote, `quiet`; a date only where it differs from the Item's; Entity pills; the machine label; on every page but the Sunday read, the block's Feedback `.actions`, revealed on hover and focus), and on a narrow window the notes drop below. The blocks sit in one `<div class="margined" data-margin="open|folded">` holding the one fold control, `{{template "margin-fold" "open|folded"}}`: every page starts open (an Item, a Story, the Briefing) except the reading page, the Sunday read, which starts folded. The state lives only in `data-margin`, toggled by `static/margin-fold.js` (plain JS, loaded by the layout, a click listener on `document` and its button's `aria-expanded` synced on `htmx:load`), so nothing is remembered across pages. Its visual vocabulary, one meaning per shape, is in classes documented in the stylesheet beside `quiet`: an Entity is a `.pill` (its name, then its Role or else its kind in a `.pill-tag`, in one hue, `--entity`, teal, apart from the link accent and every status hue; view model `pill`, built by `pillsInvolved` and `pillMentioned`, rendered by `{{template "pills"}}`/`{{template "pill"}}`), an Item a `.citation` (its Source's short name, who is speaking ("No 10", never "GOV.UK"), looked up by the web adapter from the Sources list it is given (`Deps.Sources`), then its title in `<cite>`, a link; view model `itemCitation`, built by `app.cite`, `{{template "citation"}}`; no act is shown the short name), how something was made a `.machine` label worded `<act> · call N` (view model `made`, `{{template "made"}}`), and what Feedback took out (a withdrawn or unwanted Development, a withdrawn Connection) stays, `.struck` (struck through in the quiet colour), with the reason in its margin. The pieces live in `margin.go` and `templates/margin.html`, which `page` parses into every page. A Story's page is one margined region, open: its title a block (notes such as "you started this Story" and its Feedback in the margin); its Timeline as entries (`timeline.go`, `timelineOf`), each a run of consecutive Developments from one Item, its head (`.entry-head`) giving the date and the Item's citation once, so a later Item between two runs of one Item splits them, each Development a block showing its own date only where its Fact's differs from the entry's, its margin the quote, pills with Roles, `placed · call N` and its actions; Causes, each a block reading "cause led to effect", its margin the two Facts' Items, `connected · call N` and the Connection's actions; Connected Stories, each a block with the Story's title as a link, its margin the reasons (announced together in an Item, shared Developments, Entity pills with Roles, rarest first). At its foot (`.story-foot`), outside the region and collapsed, are the missed-Development and missed-Story forms and the Owner's Feedback on the Story. A call's page and a conversation's are for diagnosis: each opens with a one-line `.summary-head`, its outcome rendered by `{{template "outcome"}}` (`templates/outcome.html`, view model `outcome` from `outcomeOf`: applied `status-supported`, refused `status-undecided`, failed `status-refuted`, a turn that continued no hue), then what is diagnosed with open (a call's Input and Output; a turn's text and the tools it called) and the bulk collapsed in `<details>` (instructions, schema, tools, what a turn was sent, a tool call's input, the raw response; a call's attempts unless there are several). A conversation's turns are blocks in an open margined region, each `<li class="block" id="turn-N">` with its anchor, outcome and tokens in its margin. Every full page carries the layout's one navigation, a flat row reaching each index (`indexes` in `web.go`); each page template declares which index it is, if any (`page(index, ...)`), and that link is marked `aria-current="page"`; pages link at their top only to their own context (a trail's Briefing, a call's work), never repeating the navigation. It logs each request it answers as one line (`request_log.go`: method, path without its query, status, `duration_ms`; never form values), through the `Log` it is given; a `5xx` is logged at error level with the error `serverError` noted on the request, and static files at debug level, so a page load is one info line. A request htmx doesn't swap (any `4xx` but `422`, any `5xx`, or no answer) is shown in the layout's `#request-errors` region by `static/request-errors.js`, plain JS with no build step, and cleared by the next request that succeeds.
  - `internal/collect`: Collection, the Sources list with each one's short name (for citations), terms (licence, attribution, what may be kept) and rate limit, reading each feed format (Atom, the ONS release search, Parliament's written statements) and the *No Source goes quiet* check, with its ports (`Fetcher`, `Store`). A Source whose feed carries only a summary declares how each entry's full text is fetched (`Source.Text`, `text.go`: GOV.UK's Content API document for the entry's path, or the written statement itself), and a new entry is kept only once its text is fetched, through the same `Fetcher`; one whose fetch fails is left out, and the feed's validators are not saved, so the next run sees it again. `Backfill` (`backfill.go`, its port `TextStore`) gives the text to unread Items collected with only a summary. Its timetable runs inside the app process, started by `main`.
  - `internal/cut`: the Cut, the first event of the event-based Record. `Sentences` lists an Item's text's sentences as `Span`s, byte offsets (start, end) into the text as kept (the publisher's HTML; `Words` reads the words at an address, tags dropped and entities decoded), never crossing a block or blank line; `Cutter.CutNew`, run by Collection after every run before the Topic check (`collect.Deps.Cut`), cuts each Item with text that has no Cut yet, by `SentenceCutter` (the Judge `sentences`, version 1: bump it whenever what `Sentences` lists could change), so the start's run cuts the Items already in the Record, once. An Item with no text yet is cut once it is given its text. A new cutter version judges forward: Items already cut keep their Cut. An Item's page shows its text as the numbered Spans of its newest Cut (`web.Deps.Cuts`, `#span-N`, with the machine label `cut · <cutter> v<version>`), as body-and-margin blocks read as its newest reading judged them (`spanOf`): each Span hydrated (`editor.Reading.Hydrated`: a stretch that refers to another shown as the words of what it refers to, followed as far as it goes, in an `<ins>` titled with the words it was), its margin whose words it is (`spoken by …`, the speaker's Span hydrated too), the Entities it mentions (`editor.Reading.Entities`, pills built by `pillOf`: the Entity's name and kind, linked to its Wikidata item if it is one; a name not yet looked up shows as read, the office for a person or else the kind) and, for a Rejected Span (`.struck`), `rejected`; the reading's call is the machine label `read · call N`, and an Item cut but not read says it awaits reading. Each Span's number in its margin links the Span's own page, a bookmarkable address, `/items/{source}/{entry}/spans/{start}-{end}` (`span.go`, `templates/span.html`; any stretch within the Item's text, listed by a Cut or not): the Span as its Item's newest reading reads it, with its Item's citation and date, its Entities and the reading's call, then its relations both ways (`follows`, `followed by`, `same as`, `contradicts`, from `web.Deps.Relations`), each linking the Span at its other end, citing its Item, and the call that made it (`related · call N`). `cut.Within` turns words quoted within a Span into their address (matched as a reader sees them, curled quotes as straight); `cut.Stretch` is `Words` keeping the space at either end, so a Span's stretches read as the Span put back together.
  - `internal/interest`: the Owner's Topics and Depths, and the check that ties Items to Topics with no model call. It selects nothing reading reads: every Item cut is read (system design: *Every Item is read, and Topics select nothing*), nor what relating relates: the ties feed no act. Collection runs the check after every run; taking up a Topic, or changing its Depth, re-runs it for that Topic over the Items not yet read.
  - `internal/feedback`: the Owner's Feedback. `Service.Give` validates which kinds each level takes, keeps the piece as given (with its Depth and when), and applies its `Effect` (worked out by `EffectOf` from the piece alone, so a changed mechanism can be re-run over all of it), in one transaction through its `Store` port. Effects are marks naming the Feedback (`withdrawn_by`, `unwanted_by`, `missed_by`), never deletions; the storage adapter keeps withdrawn records out of every act's queries. Given inline on the Briefing (`POST /briefings/{day}/feedback`), a Story's page (`POST /stories/{id}/feedback`) and an Item's page (`POST /items/{source}/{entry}/feedback`: *wrong* on each Fact, in its margin's `.actions`, and nothing else, since *new to me* is given on what the Owner reads, not on a reading), each answering `303` back to its page or `422` with the page re-rendered around the failed form; the missed-Development form offers the storage adapter's `FactsToAdd` (`facts_to_add.go`): at most `factsToAddLimit` (20, `internal/web`) of the Facts whose Items mention an Entity the Story's Items mention, ranked as `CandidateStories` ranks Stories, by the Entities each shares weighted by rarity over Stories (the shared `rarity`), then newest; where Feedback of a kind already stands on a target, that target's button renders as given, beside the Undo of that piece from the page (the web adapter matches the page's buttons against the kept Feedback, `givenIn`), and is not offered again; `GET /feedback` lists it all as given, a table newest first (When; Kind, a filled label in its own hue from the stylesheet's kind hues, the table's one hued cell; About, linked to its page with its level as a quiet prefix, a Fact's page being its Item's, which the kept-Feedback query carries with each piece on a Fact (`Kept.SourceID`, `EntryID`); Depth; How it was made, a machine label per call behind what it is about (worked out in the storage adapter's kept-Feedback query by the same lookups as the Item and Story pages), or "you made it"; Undo in the row's actions, an undone row struck through and quiet). `Service.Undo` marks a piece undone (`undone_at`, kept, never deleted) and the storage adapter's `lift` works each mark it made out again from the Feedback still standing (the earliest standing piece that makes it, or none), so a mark another piece makes stays; what an undone *missed* added is withdrawn by it and shown nowhere. Undone from each page that lists it (`PUT {page}/feedback/{id}/undone` on the Briefing, a Story's page, an Item's page, a Sunday read, and `PUT /feedback/{id}/undone`), answering `303` back. Undone Feedback is never precedent and the register does not count it.
  - `internal/register`: the register. Each hypothesis of the end state read from the Record by its declared reading rule (windows counted from the first Briefing), pure code over a constructed `register.Record`, shown at `/register`. Status lives only here, derived on every view, never stored. Opening a Briefing or a Sunday read is kept as a side record, once per day; commits come from the `commits` admin command (below), which also marks the commits that change the Editor (`internal/editor`, `internal/claude`, `internal/feedback`, `internal/sqlite/feedback.go`).
  - `internal/claude`: the Claude model adapter (Anthropic's Messages API and Message Batches API through `anthropic-sdk-go`, structured output against the act's schema). Anthropic's types stay inside it, and so do its prices (`prices.go`: `PriceOf` per model per million tokens at real-time rates, dated `PricesAsOf` with `PricesSource`; a test fails if a model in `.env.example` has none), used only by a re-judging run's estimate; read them again when a model changes or before a run whose cap matters. Its `Turn` (the `Conversation` port) uses the beta Messages API for strict tools, adaptive thinking at high effort, `fallbacks: "default"` on a refusal and prompt caching; a manual loop in the Editor, not the SDK's tool runner, so the act owns its bounds and checks.
  - `internal/editor`: the Editor. Its acts: *reading an Item* (`reading.go`), shown the Item as its newest Cut, numbered `S1`, `S2`…, one call judges what its Spans *refer to*, what they name (a name, its kind, and for a person the office in full; code drops an office given to anything else), who speaks them and which are Rejected, each stretch cited as a Span's number and words quoted within it, which code turns into an `Address` (`cut.Within`), refusing a Span not in the Cut or words not in their Span, naming both; the `Reading` carries its `Judge` (act, `ReadingVersion`, the model reported, the request's hash with the model asked for), and every Item cut and not yet read is read, with no Topic check; reading draws no Facts, and nothing new reaches the Briefing from it until it moves onto Spans (#215); and *relating a Span* (`relating.go`): once an Item is read and what its reading names looked up, its Spans not Rejected are shown, hydrated and with their speakers, beside its candidates, Spans not Rejected of Items first read before it (`ToRelate.ReadOrder`, the Item's first reading) that mention an Entity one of its Spans mentions (`relate_waiting.go`, `candidatesOf`: per Span ranked by the Entities each shares, each weighted by one over how many Items read by then mention it, then the most recent, at most `candidatesPerSpan` (10) per Span and `candidatesPerItem` (200) for the Item, not narrowed by recency), pooled and numbered `C1`, `C2`… under their Items, every Span weighed against the whole pool; one call judges each pair `follows`, `same_as` or `contradicts`, or none, refusing a relation to anything not shown (a Span of the same Item included) or two verdicts on one pair; code turns each into a `Relation` from the later-published Span to the earlier (`follows` from the one that moves on what the other said), and `Relation.Corroborates` (same as across different Sources) is worked out, never judged. An Item none of whose Spans finds a candidate (the first read, for one) is related with no call. Each pair is judged once, by the Item read second: of two read in one batch, the later-published, since a batch's results are applied in the order its requests were submitted (`PendingBatches`, by `rowid`), reading's oldest Item first. Placing and connecting are retired (#213): their outputs still in the Record are read by the Story pages, the Briefing and the Sunday read, and tests and the frozen recordings write them with `internal/editor/frozentest`, not part of the app. Each act has its own instructions, output schema and checks, and the provider-neutral ports they call: `Model` (one call, at once) and `Batcher` (a provider's batch interface). The daily acts run in batches through `Batches`: an act is a `BatchAct` (what awaits it, each piece of work with its request and how its result is checked and written), so relating (`Editor.Relating()`) plugs in beside `Editor.Reading()`; work that needs no call (`Job.Request` empty: an Item related with no candidates) is applied at once; one batch carries every act's requests, and the Claude adapter sends each to its act's model (`claude.Options.ActModels`). After each Collection run, `Batches` applies the results of batches that have ended (matched by request ID), resubmits each failed request alone, and submits what awaits as one batch; pending batches are kept in the Record. Each piece of work gets `MaxAttempts` (3) attempts, and a batch not ended or not pollable by `BatchDeadline` (48h) counts one for each of its pieces; the attempts are kept with each batch's end (`work_attempts`). A result that fails to apply for a reason other than the act's checks (its `Apply` errs, not with `ErrFailedChecks`) is no attempt and stops only itself: the batch's other results are applied, the batch is kept (same ID and submission time) holding only the requests still to apply, so their work stays in a batch and isn't submitted again, and each run applies them again from the kept results until they apply; one still failing at `BatchDeadline` counts an attempt, as a lost batch does; a result for work whose request has changed since it was sent (`RequestHash` of the request kept with the batch against the one the work builds now) is refused, counting an attempt, and the work asked again as it stands; and work marked failed is left out of `ItemsToRead` and `ItemsToRelate` by the storage adapter, listed on the Items page, and taken up again only by the `retry` admin command (below). A reading that fails its checks writes nothing and is tried again. Neither reading nor relating is shown precedents (#217 brings them back for judgements on Spans). `Editor.ReadWaiting` and `Editor.RelateWaiting` are the synchronous paths, for when no batch interface is available. Connections between Stories are derived by the storage adapter (`ConnectedStories`: the Developments two Stories share, the Items both have Developments from, "announced together", and the Entities their Facts of different Items involve in one role, rarest over Stories first; an Entity in more than `commonEntityShare` (half) of the Stories connects none), never stored; the Story page and the Sunday read's `story` tool show the same reasons.
  - `internal/editor` keeps every model call reading, relating and writing the Briefing make (`calls.go`), in a batch and through the synchronous paths alike (`Editor.callNow`), as placing and connecting did before they were retired: a `Call` holds the act and work, the request as sent (a batch's request is kept when it is submitted, with the pending batch), the model asked for (`Deps.ModelFor`/`BatchDeps.ModelFor`, the adapter's `claude.Model.ModelFor`), the response as returned (`Response.Raw`, the provider's own form, beside its reported model, usage and stop reason; nil when none came), the outcome (`applied`, `refused` by the checks, or `failed`) with its reason, and `RequestHash`, the one hash of a request (instructions, schema, input, model) that recorded runs share. Applied calls go through `KeepCall`, failed attempts with their `WorkFailure` in `EndBatch`. The storage adapter keeps each distinct text once (`call_texts`) and refuses to rewrite or remove a kept call; `GET /calls/{id}` shows one with every attempt at its work, linked from an Item's reading of its Spans (found by the reading's request hash, `spansReadingCall`) and from each Fact and Claim the earlier reading act drew (its own call, `readingCall`; the machine label "read · call N" on both), from each relation on a Span's page (found by its relating's request hash, `relatingCall`; "related · call N"), from each Development and cause Connection on a Story's page ("How it was placed", "How it was connected") and from failed work on the Items page, and records no open. The storage adapter finds a Development's call by its Item and the time it was placed, and a Connection's by the Item it was made on (`fact_connections.made_on`) and the time it was made; a Development the Owner added has none. No act is shown them. The Briefing's calls are keyed by its day (act `briefing`), each attempt kept, refused or failed ones before the failure, so a written Briefing links to its trail ("How this was written", `GET /briefings/{day}/trail`: its totals summed over the distinct calls, then a table (Development, Story, Placed, Read) whose first row is the call that wrote it, then a row for each Development it cites as written, from the storage adapter's `BriefingCitations`, each call a machine label with its tokens, "placed · call N · 2,140 tok" (`made` with `Counted`); it records no open) and a day with none written to each failed attempt; a Briefing written empty makes and keeps no call, and its page says so.
  - `internal/editor` also judges a range of the Record again with one judge (`rejudge.go`, system design: *Every judgement carries its judge, and a changed judge judges forward*), for the `rejudge` admin command: an act plugs in as a `RejudgeAct` (its name, `Version`, and `Work` over a `Range`, each `RejudgeJob` a request and an `Apply` that keeps its result as the live judge's or as a `Candidate`'s), reading as `Rereading`; relating and the Briefing add theirs as they come. `Rejudge.Price` is the dry run, calling no model: input tokens from each request's size at the tokens per byte of the act's past applied calls, output at their mean per call (or 3 bytes a token and 4000 out with none), in dollars from the adapter's `PriceOf` at real-time rates. `Rejudge.Run` prices first, refuses an estimate over `MaxUSD` (`ErrOverCap`), then calls in real time, a piece at a time with `MaxAttempts` attempts each, keeping every call, and stops before an attempt whose estimate would take the spent over `MaxUSD`. `CompareReadings` counts, per kind of judgement, what a live and a candidate reading each made and both made.
  - `internal/editor` also writes the Briefing, in real time (`briefing.go`, `schedule.go`): `Schedule` is its own clock in the app process, writing the day's Briefing at `BRIEFING_TIME` through `Model.Complete`, not the batch runner. It never waits for reading or relating: it is written at `BRIEFING_TIME` over what the Record holds then (system design: *The Briefing doesn't wait for construction*); `main` starts it only once the start's first Collection run has ended. While it is being written, the day's page polls `GET /briefings/{day}/status`, a fragment that re-polls only while it is. Each statement cites its Developments by ref, and the act's check refuses a Briefing with an untraced statement; a failure is kept, shown on the day's page, and retried after `RetryBriefing`.
  - `internal/editor` also writes the Sunday read (`sunday.go`, `sunday_tools.go`), the one act that is an agent with tools, through the provider-neutral `Conversation` port (`conversation.go`: one turn at a time, tool definitions, calls and results, the provider's own form of each turn passed back opaque as `Turn.Raw`). The act runs its own loop (bounded by `SundayReadMaxTurns` and `SundayReadTokenBudget`), its tools read the Record and Wikidata, and the agent submits through `submit_read`; the check refuses a statement citing nothing, or anything the run was not shown, and tells the agent why. `Schedule` writes it on Sundays just after the Briefing (`ScheduleDeps.SundayRead`), retried `RetrySundayRead` apart at most `SundayReadTries` times. Each attempt's conversation is kept turn by turn (`editor.KeptConversation`, with the read or its failure, in one transaction): each turn keeps only the messages new with its request (the conversation's prefix isn't kept again), the turn as returned (a refusal's too), its usage and what came of it (`continued`, `applied`, `refused` with the reason told back, `failed`), and `editor.ConversationRequestHash` of the whole request, the conversation counterpart of `RequestHash`. The conversation's page is `/conversations/{id}`, turn by turn (`#turn-N`) with tokens per turn and summed, and is the read's trail ("How this was written"), linked from the read, its failure and each Assessment (the submitting turn). The read's page is `/sunday-reads/{day}`, linked from Sunday's Briefing; an Assessment's stable address is `/assessments/{id}`, and Feedback on the read (`new to me`, level `sunday read`) and its Assessments (`wrong`, `new to me`, level `assessment`) is given at `POST /sunday-reads/{day}/feedback`.
  - The Facts, Claims and mentions the retired placing and connecting acts worked on, and the Briefing and the Sunday read still read, were drawn by the earlier reading act, before the Record's unit was the Span (`facts.go`: `Fact`, `Claim`, `FactReading`). No act draws them now: the Record keeps those it drew, and tests and the frozen recordings of the acts built on Facts write them through the storage adapter's `SaveFactReading` (in the editor's tests, `factReadingOf` and `drawSpeechFacts`; in the web adapter's, `drawFacts`). Its Wikidata look-ups, and the Facts it drew from the positions a person holds, are gone with it; what Spans name is looked up by the look-up step (below). The Record keeps the earlier act's mentions (`item_mentions`), by which the missed-Development form finds Facts. The Stories, Developments, roles and causes placing and connecting made stay in the Record, read by the Story pages, the Briefing and the Sunday read; no act writes them now. `internal/editor/frozentest` writes those acts' outputs for tests and frozen recordings, through the storage adapter's `FactsToPlace`, `CandidateStories`, `SavePlacing`, `FactsToConnect`, `FactsNear` and `SaveConnecting`, which nothing in the app calls. A Fact is tied to an Entity only by the Role connecting gives it (`fact_entities`, role required). `editor.Fact.Entities` is set only on a Reference Fact (`reference_fact_entities`); a Fact drawn from an Item carries none, and what needs its Item's mentions reads them from the Item (`ToPlace.Mentions`, `ToConnect.Mentions`, `ReadItem.Mentions`), or the Entities it involves from `Fact.Involves`. Reading refuses an answer in the earlier act's schema.
  - `internal/editor` also looks up in Wikidata what the readings name, in plain code (`lookup.go`), as its own step: `Lookups.LookUpWaiting`, run by Collection after reading (`collect.Deps.LookUp`), looks up each `LookupKey` no look-up has looked up (the storage adapter's `NamesToLookUp`, over every reading's names, a candidate's included: a look-up is keyed on the name and shows nothing, so a chosen candidate's names are already looked up), once: the name and kind, and for a person named with an office, the office and the Item's date in UTC (`KeyOf`), so "Derby" in any number of Items is one look-up. `LookUp` matches by `match` (an office's holders on the date first, else the best ranked item of the right kind whose label or alias is the name) and returns a `NameLookup` with its judge (`Looker`, `wikidata` v1). A look-up Wikidata refuses, after the adapter's own backoff, is logged and kept nowhere, so the next run tries it again; it holds up no reading, which is kept already. `KeepLookup` keeps it as a `lookup` event (`lookups`), with what it makes in one transaction: with no match, the Editor's own Entity for its name and kind if there is none (an `entity` event, `editor_entities`); with a match, a `merge` event (`entity_merges`) for each unmerged Editor's Entity of its kind made for the key's name or the item's label. Which Entities a Span mentions is a view, never stored: `Reading.Mentions` (the names inside it, or reached by following *refers to* from a stretch inside it), and `Reading.Entities` over the storage adapter's `EntitiesNamed` (each key's newest look-up: its item, or the Editor's Entity, or the item that was merged into), each a `NamedEntity` (equal exactly when the same Entity).
  - `internal/wikidata`: the Wikidata adapter (Action API: `wbsearchentities`, `wbgetentities`), polite by Wikimedia's rules (go-slow's User-Agent, one request at a time a second apart, `maxlag`, `Retry-After` backoff; a lookup answered `maxlag` is sent once more after the backoff, and one its search refuses as too busy (`cirrussearch-too-busy-error`, taken with any status) up to three times more, after `Retry-After` or else 10s doubling; nothing else is retried). Tests fake it at HTTP with `wikidatatest.Handler`, serving real responses recorded once in `internal/wikidata/testdata/` (named by request; see the handler). Recording another is one `curl` with go-slow's User-Agent and a placeholder contact, never the Owner's.
  - `internal/polite`: the HTTP adapter Collection fetches through, carrying the politeness rules (User-Agent, conditional requests, one request per host at a time, `Retry-After` backoff, daily robots.txt).
  - `internal/sqlite`: the storage adapter, with its migrations. Its event store (`0023_events.sql`, `cuts.go`) sits beside the older tables: each event is a row of `events` (its identifier `id`, its `kind`, the version of its shape `shape`, and `at`), with its detail at its own grain in its kind's tables keyed by the event's id (a Cut: `cuts`, naming the Item and its Judge, `cutter` and `cutter_version`, and `cut_spans`, the Spans numbered `n` from 1 as `span_start`/`span_end`). Triggers refuse every update and delete on them: events are append-only, and a view reads every shape it has ever been given. Events hold no text: they address the Item's text, which stays in `items`, so it can be forgotten without rewriting an event. A later kind of event adds its own tables, keyed the same way, and its own triggers: a reading (`0024_reading_spans.sql`, `readings.go`) is an event of kind `reading` (`readings`: its Item, the Cut it was shown, and its Judge, `act`, `version`, `model`, `request_hash`), and each judgement it made an event of its own tied to it by `reading_id` (kinds `refers_to`, `name`, `speaker`, `rejected`; tables `refers_to`, `span_names`, `speakers`, `rejections`), every address byte offsets into the reading's own Item, so `KeepReading` refuses a judgement addressing another Item and keeps nothing. `ItemsToRead` is every Item cut and not yet read by a live judge, with its newest Cut; `NewestReading` the reading of an Item a view reads, with its judgements: the newest live judge's (`newestLiveReading` in `judges.go`, the one subquery every view of readings goes through, the Items list's included). Candidate judges (`0026_candidates.sql`, `judges.go`) are events of kind `candidate` (`candidates`: act, version, model and the range), each reading a candidate made tied to it in `candidate_readings`, written with the reading (`Reading.Candidate`); choosing one is an event of kind `choice` (`candidate_choices`), rewriting nothing. A reading is live if no candidate made it or its candidate was chosen, and a chosen candidate's readings count as made at the choice, so the choice outranks every live reading before it and a live reading after it outranks the choice. `ItemsIn` is the Items cut and published in a range, read or not, for judging again; `PastUsage` the size and tokens of reading's applied calls that answered a reading, which a run's estimate scales from. A relating (`0027_relating.sql`, `relating.go`) is an event of kind `relating` (`relatings`: its Item, the reading its Spans were shown as, and its Judge; model and request hash empty for one made with no call), and each relation it judged an event of kind `relation` (`relations`: its kind, `follows`, `same_as` or `contradicts`, and two addresses, from the later-published Span to the earlier, of two different Items, one of them the relating's own, which `KeepRelating` checks). `ItemsToRelate` is every Item read, not yet related and not failed whose reading's names all have a look-up, in the order Items were first read (`firstRead`), each with its Spans not Rejected and the Entities each mentions; `SpansMentioning` is the Spans not Rejected of Items first read before a given reading that mention one of the Entities given (the Record-wide "Spans mentioning an Entity", worked out from readings and look-ups, never stored), each with its Item, hydrated words, speaker and Entities; `ItemsMentioning` how many Items read by then mention each; `RelationsOf` a Span's relations either way, each with the Span at its other end, its Judge and its call.
  - `internal/server`: serving with graceful shutdown.

## Commands

- **Inner loop:** `go test ./...` (add `-run <Test>` or a package path to narrow it).
- **Full check:** `uvx --from pre-commit==4.7.0 pre-commit run --all-files`. It runs every hook below; CI runs exactly this. A `pre-commit` already on PATH works too, if it is at least 4.5.0. Install the git hook once per clone with `uvx --from pre-commit==4.7.0 pre-commit install`.
- **Re-record the Editor's recorded runs** (deliberately, when an act's instructions, schema or model change; it calls the real model five times per fixture, more where the checks refuse an attempt, and costs money): `go test -count=1 -timeout 90m ./internal/editor -run TestRecordedReadings -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `READING_MODEL` set in the environment (the default 10m test timeout is too short for five samples of every fixture); for relating, `-run TestRecordedRelatings -record` with `RELATING_MODEL` set. Relating's recorded test reads its frozen readings, looks their names up in a Wikidata that finds nothing (`noMatch`, so each name is the Editor's own Entity and no recording calls the network), and relates each fixture in the order they were published; its properties are judged on the Holyrood speech: it *follows* the press release that said what the Prime Minister *will* do, and its "most centralised" line is *same as* the release's and not corroboration (one publisher). A fixture whose Spans find no candidates (the first, with nothing read before it) makes no call, and its samples keep none (`"output": null`). Reading's fixtures are each shown as the sentence cutter cuts them (`fixtureToRead`), and its properties are judged per fixture where the fixture carries the case (asserted present first): a bare "X said:" Span is Rejected (`bareAttribution`); each Span of a quotation is given as its speaker who the Item names before it (`quotations`); a pronoun refers to its antecedent and "the city" to Derby (`references`); and the readout naming the Prime Minister only by office names a person with that office. **A recording is samples, judged by a rule** (system design: *A recording is one sample, and a property is judged by its pass rate*): each fixture is sampled 5 times (the rule is `dailyRule` in `recorded_samples_test.go`; the Sunday read takes 3, `sundayReadRule`, below), each sample run as in use, up to `editor.MaxAttempts` attempts against the act's checks, and kept at `testdata/recorded/<act>/<fixture>/<k>.json` (the last attempt, with the refused ones before it under `earlier_attempts`), written attempt by attempt as it arrives. The suite replays every sample and judges each property per fixture: *passes its checks within its attempts* over all 5 samples, each test-only property over the samples that passed; supported at 5 of 5, refuted at 3 or fewer, undecided at 4. Refuted or undecided fails the test, as does a fixture with fewer samples than the rule, or samples answering different requests. An undecided fixture is read again on 5 fresh samples, judged alone: delete its directory and record again (`-record` keeps the samples already kept for the request the act sends now, so it also resumes a stopped recording, and draws only what is missing or stale). Don't add samples to push a count over the line, and don't change a check or property to pass. For relating, whose fixtures build on each other, each sample of a fixture runs over the Record the fixtures before it left, each carried on by its first sample to pass, so a fresh reading of one fixture makes the later fixtures' samples stale and `-record` redraws them. Each act is replayed over its own frozen copies of the recordings it rests on, under `testdata/recorded/<act>/inputs/<upstream act>/` (relating over readings of Spans; the Briefing and the Sunday read over the earlier reading act's readings of Facts, loaded as it wrote them by `factReadingOf`, and the retired placing's and connecting's recordings, written by `frozentest`), never over the upstream recordings themselves, so re-recording one act leaves every other act valid: re-record only the act you changed. Target the package: other packages don't define `-record`. The responses land in `internal/editor/testdata/recorded/`; commit them, and the diff shows what changed. The suite only replays them and never calls a model. Each recording keeps the hash of the request it answered (`editor.RequestHash`, with the model the act is pinned to in `.env.example`), and a replay whose act now builds another request (changed instructions, schema, input or pin) fails as stale, naming the command that re-records it; an act's frozen copies of upstream recordings are replayed unchecked, since the act that made them checks them. A fixture with no samples fails with a message naming this command. Fixtures (`internal/editor/testdata/govuk/`) come only from admissible Sources, with their licence attribution.
- **Re-record the Briefing** (when the act's instructions or schema change): `go test -count=1 ./internal/editor -run TestRecordedBriefing -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `BRIEFING_MODEL` set. It replays its own copies of the readings, placings and connectings (`testdata/recorded/briefing/inputs/`) into a Record with fixed Topics and Depths, and writes the day's Briefing, sampled 5 times by the rule above (`testdata/recorded/briefing/saturday/`).
- **Refresh an act's frozen copies** (to bring a downstream act onto an upstream act's newer recordings): its own change, never part of the change to the upstream act, made once that act's new behaviour is accepted on its own recordings. Copy every upstream act's current recordings together over the act's `inputs/`: a frozen copy is the fixture's first sample, copied as it is (for relating, each `testdata/recorded/reading/<fixture>/1.json` to `relating/inputs/reading/<fixture>.json`), and only from recordings whose every property is supported, so the first sample's last attempt is the one that passed. Then re-record that act alone. Never copy one upstream act without the others: new readings with old relations is a run no Editor makes. Refresh the Sunday read only on the Owner's say, since it costs dollars. Until a refresh, two checks cover the gap, with no recording of their own: the chain replay (`TestRecordedChainTracesEveryBriefingStatementToAQuote`, over the Briefing's copies and each of its samples that passes) and the compatibility check (`TestEachActsCurrentRecordingsAreTakenByTheActsDownstream`: reading's current recordings, each fixture's first sample, fed through relating on a fake model, which must be asked about every fixture relating's own recordings were asked about, its answers passing the checks; `TestTheCompatibilityCheckFailsOnAReadingRelatingCannotTake` is its negative case. The Briefing's and the Sunday read's copies are of the retired acts, which no current recording feeds). Each downstream act's own recorded test replays over its own directory copied alone (`ownDirectory`; `TestEachRecordedActReplaysOverItsOwnInputsAlone` does so for the Sunday read), so an act that reads another's recordings fails. The recorded tests run in parallel (`t.Parallel`): with five samples per fixture, `go test -race ./internal/editor` takes about 75s.
- **Re-record the Sunday read** (only on the Owner's say: when the act's instructions, tools or checks change, or as a refresh onto newer recordings of the earlier acts; it runs the agent on Claude Opus 5.5 three times and costs about a dollar): for a refresh, first copy each fixture's first sample of `testdata/recorded/{reading,placing,connecting}` together over `testdata/recorded/sunday/inputs/{reading,placing,connecting}/` (`reading/<fixture>/1.json` to `sunday/inputs/reading/<fixture>.json`, and so on), in its own commit, then `go test -count=1 -timeout 90m ./internal/editor -run '^TestRecordedSundayRead$' -record`, with `GOSLOW_ANTHROPIC_API_KEY` and `SUNDAY_READ_MODEL` set (`-max-tries N` bounds each sample's tries below the act's own `SundayReadTries`, to keep a run within the retries its brief allows). It takes **3 samples** (`sundayReadRule`: every property supported at 3 of 3, refuted at 1 or none, undecided at 2, which is read again on 3 fresh samples, judged alone: delete `sunday/<k>/` and record again). Each sample runs as in use, up to `SundayReadTries` tries, each a whole conversation over a fresh copy of a Record built from its own copies of the readings, placings and connectings (`sunday/inputs/`, so re-recording the earlier acts leaves its replay valid) with the Briefing's Topics. Each try is kept as it runs, turn by turn, at `testdata/recorded/sunday/<k>/try-<n>/conversation.json` (every turn in the provider's own form, with `editor.ConversationRequestHash` of its request, the hash a kept turn carries), with Wikidata's answers to its lookups beside it (`wikidata/`, fetched with a placeholder contact), so the replay makes no network call. A turn whose request the act no longer sends fails the replay as stale; `-record` keeps the tries that still replay and draws afresh a stale one or one left unfinished.
- **Report each act's yield on every re-recording above, and paste the table into the PR body**: extract the recordings being replaced (e.g. `git archive -o <scratch>/old.tar origin/main internal/editor/testdata/recorded`, then `tar -xf <scratch>/old.tar -C <scratch>/old`), then `go run ./internal/editor/yield <scratch>/old/internal/editor/testdata/recorded internal/editor/testdata/recorded`. It prints, per act and per fixture, before → after: for reading, the Spans the fixture is cut into (from the fixtures beside either directory, `../govuk`), and those Rejected, the names, speakers and *refers to* it judged (a reading of the earlier act, which drew Facts, judged none); relations by kind (*follows*, *same as*, *contradicts*) for relating, a sample with no call counting none; Developments and new Stories for placing, from recordings before it was retired; Connections for connecting, and what it leaves out, which its checks can't see: the mentions it was shown (those of its frozen copy of the fixture's reading, `connecting/inputs/reading/<fixture>.json`, matched by name) that it involves in no Fact, and the Facts it gives no Roles (both counted, never judged); statements and Stories for the Briefing, with totals, and marks fixtures added or removed. A fixture's samples show as the range they drew, least–most, each by its last attempt, and a total as the range from every fixture's least to its most. Its last table, *agreement*, is how alike each fixture's samples are in what each Fact involves (the mean pairwise Jaccard index of each Fact's set, over every pair of samples and every Fact, and a mean over the fixtures): for connecting, by Entity and Role and by Entity alone. It reports and never fails: whether a shift is a loss is a reading. It calls no model, counts nothing in `inputs/` (frozen copies of upstream recordings; connecting's are read only for the mentions it was shown) and acts it doesn't count (the Sunday read), and is a dev tool under `internal/`, not part of the app binary.
- **Record commits for the register** (the quiet window, and Due on a change to the Editor): `git log --format='commit %H %cI' --name-only | docker compose run --rm -T app commits` (outside docker, pipe into `go run ./cmd/go-slow commits` with the same environment). The app can't see the repository, so commits are piped in; ones already kept are skipped, so pipe the whole log each time. An admin command of the binary, with the app's own config.
- **Retry failed work** (work that failed all its attempts, listed on the Items page): `docker compose run --rm app retry [reading|relating]` (outside docker, `go run ./cmd/go-slow retry ...`). It clears the failed marks on that act's work, or every act's with no act named, resetting the attempts, so the next Collection run submits it again. Admin commands live in `cmd/go-slow/admin.go`, tested end to end in `admin_test.go` and `backfill_test.go`.
- **Backfill Items' text** (one-off, for Items collected before their Source's text was fetched): `docker compose run --rm app backfill` (outside docker, `go run ./cmd/go-slow backfill`). It fetches, politely, the full text of every unread Item of a Source that declares a text fetch and has none, keeps it, and runs the Topic check over those Items again; Items already read are left as they were read. An Item whose fetch fails is logged and left for another run of the command.
- **Re-judge a range of the Record** (only on the Owner's say; it calls the real model and costs money; never run against the Owner's Record by an agent without that say): `docker compose run --rm app rejudge reading --from YYYY-MM-DD --to YYYY-MM-DD` (outside docker, `go run ./cmd/go-slow rejudge ...`) is the dry run: it prints the requests, the estimated tokens in and out and their price in dollars at real-time rates, with the date of the prices, and calls no model and writes nothing. The days are the Items' publication days, both included, in `TZ`. Add `--confirm --max-usd N` to run it, in real time, stopping before a call that could take it over `N` dollars; it judges as the live judge on the act's configured model (`READING_MODEL`), so views read its judgements as the newest. Add `--candidate` (and `--model M` for another model) to keep them as a candidate instead, read by no view; `rejudge candidates` lists the candidates, `rejudge compare <id>` prints, Item by Item and in total, each kind of judgement the live reading and the candidate's made and both made, and `rejudge choose <id>` makes it the live judge from then on, as an event, once `READING_MODEL` names its model (set it first, then choose). Tested end to end in `cmd/go-slow/rejudge_test.go`; the command is `cmd/go-slow/rejudge.go`.
- **Lint and format:** `go tool -modfile=tools/go.mod golangci-lint run ./...` and `... golangci-lint fmt`.
- **Run locally:** `cp .env.example .env`, then `docker compose up --build`, and open http://localhost:8080 (the port is published on `127.0.0.1` only; the Record is the host folder `RECORD_DIR`, bind-mounted). For daily use, see the *Runbook* below. The app logs JSON lines to stdout and stops cleanly on SIGTERM (`docker compose stop`). Outside docker: `go run ./cmd/go-slow` with the variables in `.env.example` set.

## Runbook: go-slow on the laptop

go-slow runs on the Owner's laptop, from this repo's image and `docker-compose.yml`, published on `127.0.0.1` only (system design: *go-slow runs when the Owner starts it*). Nothing keeps it running: start it each day to read.

- **Docker without Docker Desktop:** the containers run in Colima, which needs no login. Once: `brew install colima docker docker-compose`, add `"cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"]` to `~/.docker/config.json` so `docker compose` finds the plugin, then `colima start --memory 4 --cpu 4` (it switches the docker context to `colima`, and later starts keep the size). The VM needs the 4 GiB: compiling `anthropic-sdk-go`, one 120k-line generated package, peaks at about 1.4 GB in one compiler process, and Colima's default 2 GiB VM kills the image build.
- **Once:** `cp .env.example .env`, set your own `COLLECTION_CONTACT` and `GOSLOW_ANTHROPIC_API_KEY`, and set `RECORD_DIR` to an absolute path outside the repo (the folder holding the Record; `mkdir -p` it). Copying that folder while go-slow is stopped is a backup.
- **Start each day:** `colima start` (if it isn't running; `colima status` says), `docker compose up -d`, then open http://localhost:8080. The start's Collection run fetches what came in overnight and submits it in batches; at `BRIEFING_TIME` the Briefing is written over what the Record holds then, without waiting for the batches.
- **Stop:** `docker compose stop` (SIGTERM; the app drains and exits). `docker compose logs app` shows its JSON log.
- **Upgrade:** `git switch main`, `git pull`, then `docker compose up --build -d`. Migrations run on start.
- **Record commits for the register:** `git log --format='commit %H %cI' --name-only | docker compose run --rm -T app commits` (see *Commands*). Pipe the whole log each time.

**An agent starts the day's run when it notices it hasn't been done** (the Owner's standing say, 2026-10-27): if `docker compose ps` shows no app running on a day of work, the orchestrating agent runs *Start each day* (rebuilding with `--build` when `main` has moved since the image was built) and tells the Owner. That is the one way an agent touches the Record: never a sub-agent, never `docker compose run` of an admin command, a migration by hand or a copy, move or edit of `RECORD_DIR`, without the Owner's say for that act. The Record is the Owner's.

`COLLECTION_CONTACT` is still the example placeholder, on the Owner's call while go-slow's volume is low (2026-10-27); a real contact goes in before it fetches much more.

## Config

Only from environment variables, every one listed with a safe local value in `.env.example`, and all required: a missing one fails at start. The real `.env` is gitignored. Add a variable to `internal/config` and `.env.example` together. The model each act runs on is a variable (`READING_MODEL`, `RELATING_MODEL`, `BRIEFING_MODEL`, `SUNDAY_READ_MODEL`, each a Claude model, since Claude is the one adapter), always a pinned model ID, never an alias the provider can move (`claude-haiku-5-5` and `claude-opus-5-5` are fixed snapshots; how that was checked is in [`docs/research/models.md`](docs/research/models.md)). **A model change is a re-record, like an instructions change**: the model is part of the act's request, so re-record that act's recordings on the new model (*Commands*, above) in the same change. Each result keeps the model the provider reports, not the one configured; `BRIEFING_TIME` is when the Briefing is written and due by, `HH:MM` in `TZ`; `GOSLOW_ANTHROPIC_API_KEY` is a `config.Secret`, which never formats as its value. Never print, log or commit a real key.

## Go toolchain

- **Go is pinned by the `go` directive in `go.mod`** (1.27.3), the same in `tools/go.mod`. A local Go that is older downloads the pinned toolchain itself (`GOTOOLCHAIN=auto`, the default), CI's `actions/setup-go` reads `go.mod`, and the `Dockerfile`'s `golang:` tag repeats the version. Upgrade all four in one PR.
- **Tools are pinned in their own module**, `tools/go.mod` (`tool` directive), and run with `go tool -modfile=tools/go.mod <tool>`. A separate module keeps golangci-lint's hundreds of dependencies out of the app's `go.mod` and build. golangci-lint is at v2.14.0; its config is `.golangci.yml` (the `standard` linters plus a few for HTTP, SQL and errors; gofmt and goimports as formatters).
- **SQLite is `modernc.org/sqlite`**, pure Go, so the binary builds with `CGO_ENABLED=0` and runs on a distroless static image. Migrations are embedded SQL files in `internal/sqlite/migrations`, applied in name order by `sqlite.Open`, with the count applied kept in `PRAGMA user_version`. Never edit a migration that has been merged; add the next one. Migrations run on one connection with foreign keys off, each checked with `PRAGMA foreign_key_check` before it commits, so one can rebuild a table others refer to by SQLite's procedure (Web apps Guide, *Storage*: create `new_X`, copy, drop `X`, rename `new_X` to `X`). `0014_sunday_read.sql` rebuilt `feedback` in the other order (renaming the old table first, under `PRAGMA legacy_alter_table = ON`); it is merged, so it stays, but the next rebuild follows SQLite's order.
- **htmx is vendored** at `internal/web/static/htmx-2.0.10.min.js`, byte-identical to the npm release (sha256 `71ea6718…c0de`), and excluded from the whitespace hooks so it stays so. Upgrading is replacing the file and the `<script>` in `templates/layout.html`.

## Checks and CI

- pre-commit hooks: the Global Guide's (`pre-commit-hooks`, actionlint, shellcheck; actionlint comes from `actionlint-py`, with `shellcheck-py` in its `additional_dependencies` for the shellcheck on its PATH, as the Rust Guide does), then `go mod tidy -diff` for both modules, `golangci-lint fmt`, `golangci-lint run` and `go test -race ./...`. The Go hooks are `language: system`, so they need `go` on PATH.
- CI is `.github/workflows/ci.yml`: one job, **`pre-commit`**, on every PR, and on pushes to `main` that change `go.mod`, `go.sum`, `tools/` pins or `.pre-commit-config.yaml`. **The required status check is `pre-commit`.** Renaming the job breaks merging once the `main` ruleset exists (it is created after CI first reports under this name).
- Actions and images are pinned to exact versions (the distroless base by digest).

## Known traps

- **Never name go-slow's key `ANTHROPIC_API_KEY`.** Claude Code reads that variable too: set in the shell `claude` is launched from, it switches Claude Code from the claude.ai login to the key, for its own requests and billing, and claude.ai connectors stop working. go-slow reads `GOSLOW_ANTHROPIC_API_KEY` instead, which agents inherit without Claude Code taking it. *Remove when:* never, while go-slow is built with Claude Code.
